# Sync

An Expo interval timer that coordinates work/rest rounds with local or web audio. Core timer, local music, routines and activity work offline for free. Supabase Auth adds accounts; server-verified Sync Pro subscriptions enable private cloud backup, device sync and an ad-free experience. Eligible Free accounts and guests can see a labelled Discover banner and optional full-screen ads at session boundaries when ads are configured. Active sessions, including rest and pause, remain free of ads. Spotify is restricted to owner development builds pending public quota and commercial permission. Current release work targets **iOS only**; see [release readiness](docs/app-store-release.md), [subscription validation](docs/subscription-validation.md) and [AdMob setup](docs/admob-setup.md).

## Run

Use Node.js 22.23.4 (the tested version in `.nvmrc` and EAS), then:

```sh
npm ci
npm start
```

Use an Expo Go client compatible with **SDK 54** for the supported core features. RevenueCat purchases and Google Mobile Ads require a native development build; an older binary without the ads modules keeps the free app usable without loading ads. Native Liquid Glass requires iOS 26 and a compatible client/build. Older systems and Reduce Transparency use the readable fallback. iOS and Android dependencies are aligned with SDK 54.

```sh
npm test
npm run check:release -- --platform ios --profile production
npx expo install --check
npx expo export --platform ios --platform android --output-dir dist
```

The export command verifies JavaScript/native-platform bundle generation; it does not build or sign an App Store/Play Store binary. A native development build is needed to validate device-specific permissions and production OAuth redirects.

The release preflight checks supplied local variables and inherited `eas.json` values without printing credentials. EAS environments and `EXPO_PUBLIC_BUILD_PROFILE` are explicit per profile; preview/production keep ads and Spotify disabled. The iOS local/profile format check passes. Expo is linked to `@feridunalacam/syncapp`, with the public Supabase URL/publishable key, public iOS RevenueCat SDK key and entitlement ID saved to all three EAS environments. Internal distribution pages require project access. Ignored `.env.local` values are not uploaded automatically. Signing, store approval and real paid lifecycle validation remain separate gates; Android has no Play account/public RevenueCat key and is outside the current release scope. See [Expo environment variables](https://docs.expo.dev/eas/environment-variables/). RevenueCat configuration rejects private/wrong-platform keys and permits Test Store keys only for debug development, following [RevenueCat's Test Store restrictions](https://www.revenuecat.com/docs/test-and-launch/sandbox/test-store).

## Architecture

- `src/domain/routines.js`: routine normalization, validation and the shared interval timeline.
- `src/domain/workout.js`: pure session state transitions, pause/resume, skipping, elapsed time and history records.
- `src/domain/audio.js`: one music source per interval, including legacy metadata handling.
- `src/context/WorkoutContext.js`: owns the active session above the tab navigator. Screens consume actions and state.
- `src/screens/Home/TimerLogic.js`: React timer adapter and foreground catch-up. Timing rules stay in the domain.
- `src/hooks/useAudioController.js`: serialized playback commands with stale-command protection and deferred playback while paused.
- `src/services`: Spotify and device audio adapters.
- `src/services/ads`: pure account/placement eligibility, environment configuration and a consent/initialization controller with stale-result guards. `AdsContext` owns the process-wide native runtime and presenter barriers. Discover and safe Timer boundaries acquire placement leases; `useSessionAds` guards Start/Continue through consent and native dismissal.
- `src/lib/platformStorage.js`: secure native credential persistence and migration from the previous plaintext record. Other local content uses the existing storage keys.
- `src/components/common/GlassSurface.js`, `Surface.js`, `ScreenHeader.js`, `Sheet.js`: shared visual components. Glass is reserved for floating navigation and utility controls; opaque surfaces distinguish content cards, inputs and sheets.

## Navigation and interface

The four tabs are Timer, Training, Discover and Profile. Training opens the routine library directly; its Activity button pushes history onto the same stack. The back button returns to routines. Opening a routine in Timer selects it without starting playback. Timer picker choices and incoming routine shortcuts require confirmation before replacing an active or paused session; choosing its current routine preserves progress. Newer choices and account unmounts retire old confirmation callbacks.

The interface uses graphite surfaces with lime accents in dark mode and an olive accent in light mode. The surface hierarchy is shared across Timer, Training, Discover, Activity and Profile. Content cards use solid graphite or white; fields use a quiet inset fill; modal sheets have an opaque background. Glass remains on floating navigation and utility controls. Lime/olive accents identify actions, selections and interval progress rather than tinting whole content panels. Profile and activity summaries are unboxed, and compact playlist/round layouts are retained. This follows Apple’s distinction between [content surfaces and the Liquid Glass control layer](https://developer.apple.com/design/human-interface-guidelines/materials). Work/rest strips visualize real interval proportions; individual durations are edited in a minute/second sheet. Playlists appear as a horizontally swipeable strip directly inside the routine editor, with Work/Rest targeting and a Shuffle action on each card; and advanced audio controls expand inside the editor. Discover has one labelled anchored-adaptive banner placement in its fixed header, outside the feed scroll. Search, an empty feed, detail overlays, active or paused workouts, music playback and audio synchronization suppress the placement.

## Behavior

Every round can have its own timing and music. Changing the global work/rest picker applies timing to all rounds; customize individual rounds afterwards. A zero-length rest is valid. The final round has no trailing rest. Preparation time, if configured, is included in the planned and elapsed session time; paused time is excluded.

Starting a session snapshots the routine so edits cannot mutate the running session. Switching tabs preserves the active session. Ending early saves actual progress; cancelling during preparation does not create a workout. A replayed round counts only once toward completed rounds. Skipped intervals are recorded explicitly.

Account records are isolated from guest mode and from other accounts. Existing guest data is imported only after the user explicitly chooses Import in Profile. Existing saved content is retained. Empty routine lists remain empty after restart. New installations do not receive fabricated workout history. Legacy history without actual duration uses its planned duration as a fallback, since past real elapsed time cannot be reconstructed.

Local read failures and malformed saved JSON stop hydration behind a Retry screen rather than overwriting recoverable records with defaults. The local core does not wait for cloud verification to mount. Explicit auth writes use one operation queue, with the pinned SDK's process lock also covering automatic refresh; abortable deadlines include auth/account-deletion response bodies. Training and Activity use windowed lists. History deletion targets a session identity, and asynchronous share captures cannot publish for a newer selection or a deleted record.

An unfinished, accepted password-recovery form is remembered in secure native storage, bound to the same account and Auth session. Its bounded hydration and stale bootstrap/completion guards have offline regression coverage; completing a real reset and terminating/reopening native recovery still need device validation. Pending store purchases remain pending when server verification fails, without granting Pro or allowing another checkout. Cloud replacement retains exact local values in a rollback journal until commit; interruptions before commit recover before later reads/writes. If a complete commit wins a workout pause and rollback cannot be reserved, the cloud copy is retained and consumers reload once idle. Guest imports reserve the account before the first copy, so interrupted copying cannot duplicate a claim across accounts; cleanup retries preserve later guest edits. Deletion drains account writes before releasing an unfinished import reservation.

Discover contains clearly marked sample routines and locally saved posts. Share images/text can be exported using the device clipboard/share sheet. Saving to Discover is not online publishing.

Advertising never unlocks the free core. Free sessions may show a preloaded full-screen ad before a NEW Start or after the user presses Continue on an ended-session summary. There are no ads during an active session, including rest or pause; resume, phase skips and arbitrary tab changes never trigger an ad. No-fill or unavailable inventory is skipped without waiting for a load or allowing a late popup. Accepted routine choices and Start/Continue actions must supply two distinct real actions before the first and each later interstitial; a separate 120-second cooldown applies. The SDK stays muted, and Start waits for real native dismissal, foreground restoration and current identity/routine checks before the timer or music begins. Pro, unknown subscription verification, purchase/restore activity and account transitions suppress both formats and the automatic consent/SDK path. UMP consent and Google Mobile Ads are loaded only for an eligible, foreground, focused placement; an explicit Profile privacy-choices action can open UMP without initializing ads. Requests ask for non-personalized ads and the app does not request ATT permission. This does not mean no advertising data is processed: the SDK's publisher first-party ID default remains enabled. Sync does not pass account, routine or music data to the ads integration. Both platform app/banner/interstitial IDs are configured. The updated session-ad disclosures are published as Sites version 4 and were checked on the public privacy page. The iOS draft Marketing URL is saved; the store listing and app-ads.txt crawler association remain unverified. European/US UMP messages are published for both apps. Production ads remain explicitly disabled while account/store review, privacy answers and production/regional validation are pending; development uses Google's test inventory. See [AdMob setup](docs/admob-setup.md).

## Spotify and media

Spotify availability requires a debug build outside the preview/production profiles. A release flag cannot bypass this gate. Release builds retain saved credentials/assignments without refreshing or contacting Spotify, hide connection/library controls, and explain how to replace Spotify audio when starting an older routine. Development playback details and earlier tests below do not establish public or commercial approval.

Spotify uses Authorization Code + PKCE with a fresh verifier/state for each attempt and the stable `syncapp://spotify-callback` redirect. This URI has been registered in the owner’s Spotify dashboard. Expo Go does not support this login flow; use `npm run ios` for a native development build (Xcode and CocoaPods required). The iOS bundle identifier is `com.feridun.syncapp`. A public client ID may be supplied through `EXPO_PUBLIC_SPOTIFY_CLIENT_ID`; no client secret belongs in the app. Playback controls require an eligible Spotify account and an available playback device. Device selection rejects restricted or unidentified devices, preserves the active-device choice, and never treats a failed transfer as successful activation. Authentication and real playback must be tested with the owner's account; simulated service tests do not prove account eligibility.

Native tokens are stored with Expo SecureStore. Refresh requests are deduplicated, rotated refresh tokens are saved, and a late refresh cannot restore a disconnected or replaced account. Expiration is checked before requests and when the app returns to the foreground. Plaintext legacy tokens are removed only after a successful secure write. Web credentials are kept only in memory. Disconnecting music leaves routines and history intact.

Playlist items use Spotify’s current `/items` endpoint with pagination. Development-mode permissions can restrict access to playlists the user does not own or collaborate on. The picker distinguishes empty libraries from access/network errors. Searches and playlist loads ignore stale results after closing or changing source.

The routine editor uses compact, horizontally scrollable playlist rows with small covers and separate accessible shuffle controls. Work/Rest assignment remains available; tapping a playlist opens its tracks. Playlist search is always visible without an extra reveal button. The library refreshes automatically on screen entry, on returning to the foreground, and 60 seconds after each completed refresh while the editor is focused and the app is active. Requests never overlap; existing rows stay visible during refresh or transient failure. There is no permanent manual refresh button.

Device and Browser sources remain available in the music picker; Spotify appears only in eligible owner development builds. Device-library permission is requested only after the user chooses Browse, with audio-only access on Android; Files remains available if permission is denied. Camera access is used only for an explicitly chosen profile photo. Unused microphone, biometric and photo-write purpose declarations are disabled.

Imported media and profile photos are copied to the app document directory instead of leaving saved references in the disposable cache. Files saved by older versions may still point to a cache location; reselect them if the operating system has removed them. Built-in alerts are bundled with the app. Spotify playback cannot be used as an independent overlay alert.

Physical-device background/lock-screen audio, Android media-library permissions, share-sheet destinations and cold-start deep links still need device testing. The timer catches up when the app resumes, but JavaScript suspension can delay audio commands; force-quitting does not restore an active session.

The Timer and Profile include a shared Spotify playback-device picker whenever Spotify is connected, including mixed-source routines so the next Spotify device can be chosen in advance. It lists devices returned by Spotify, identifies the current device, disables restricted/unidentified devices and preserves paused versus playing state. Selection is verified against playback state rather than treating HTTP acceptance as completion. An accepted transfer that leaves the original song on its original device, or an empty selected player, can restore that song once at the last observed position. A newer third-device choice, a different song, a pause, missing state or restriction prevents recovery. Device selection and workout mutations share a single queue; external device changes are adopted without resetting the workout. Resume preserves the Spotify context, and unsupported volume controls are skipped. No OS/model-name branching is used for transport behavior.

## Working on the code

Use a feature branch, keep domain changes independently testable, run the regression suite, then check the affected screens. `npm run format` applies the shared Prettier configuration. See `docs/architecture.md` for the design decisions and extension points.

### Simulator Keychain requirement

Spotify login must persist credentials in iOS Keychain. Do not build the simulator app with `CODE_SIGNING_ALLOWED=NO`: this omits the simulator entitlements and Keychain returns OSStatus -34018. Use Xcode simulator signing so the application identifier is embedded as simulated entitlements. Manually attaching iOS Keychain entitlements with `codesign` is not equivalent and can prevent the simulator app from launching. On machines where Documents is cloud-managed, put build products in a local temporary directory to avoid Finder metadata causing signing failures. Physical-device builds need normal Apple development signing.

## Timer transitions and navigation finish

Timer intervals retain the current phase and the next two phases, including the final phase, with a Now/Paused marker. Stable per-routine phase keys use short entering, exiting and layout transitions instead of removing the entire section during the final round. Animation behavior respects the system reduced-motion setting through Reanimated's [layout transitions](https://docs.swmansion.com/react-native-reanimated/docs/layout-animations/layout-transitions/).

The custom tab bar keeps the existing palette. Its GlassSurface uses native GlassView on supported iOS devices when reduced transparency is off; other configurations use the existing fallback. A subtle accent tint, neutral highlights and a moving selected-tab highlight make the material more legible. This is a custom tab bar using native glass surfaces, not the system UITabBar or a claim of native liquid morphing on every platform.
