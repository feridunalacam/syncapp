# Google and Apple account sign-in

The first signed-out launch offers the account sheet with **Continue with Apple**, **Continue with Google**, email/password and **Continue without an account**. Continuing as a guest remembers that choice on this installation. Profile keeps account access available. Signup also offers both providers; password recovery does not.

## Implemented flows

- Google uses Supabase's browser Authorization Code/PKCE flow and `syncapp://auth/callback`. A fresh flow identifier is checked against the returned callback. Browser and Linking delivery share one exchange, and the browser does not hold the session-operation queue. Account changes, unmounts and cancelled attempts cannot apply late results. User cancellation returns to the form without an error.
- Apple uses `expo-apple-authentication` **8.0.8**, pinned to Expo SDK 54, on supported installed iOS builds. The system button and sign-in sheet request only email. A fresh random nonce is hashed with SHA-256 for Apple's request; Supabase receives the raw nonce with the identity token for verification. Returned state is checked. Nonces/tokens are never logged or added to ordinary account records. Older native clients and other platforms can use the browser fallback when Apple's web OAuth configuration exists.
- Provider availability is read from the existing project's public `/auth/v1/settings` endpoint on selection, with a bounded timeout. Disabled providers produce a plain explanation while email and guest mode remain usable. The old `EXPO_PUBLIC_AUTH_*_ENABLED` flags no longer control button visibility. These buttons do not imply an activated provider.
- Password sign-in, signup and native ID-token saves use one narrow credential-write adapter around the same storage-key `processLock` used by SDK refreshes. Pinned auth-js 2.119 does not acquire that lock inside those three methods. Real-SDK/chunked-storage regressions reproduced an old-account refresh replacing the newly chosen account; tests cover all three entry points, both native operation orders and initialization/failure release. Native cancellation/account identity is checked again after acquiring the lock, and the cancelled result is carried back to the account sheet. Already locked SDK methods are not wrapped again. The explicit storage key matches the SDK's existing default, preserving installed sessions.

## Concrete activation steps

1. In the existing [syncapp Google Cloud project](https://console.cloud.google.com/auth/clients?project=syncapp-478914), create a **Web application** OAuth client named **Sync Supabase sign-in**. Its authorized redirect URI is exactly `https://iyipvwlhiwfaeyfoyakr.supabase.co/auth/v1/callback`. The existing iOS client is not a replacement for this browser-flow client. Configure the consent audience/branding and only the required `openid`, email and profile scopes. Do not request YouTube/music access for account login.
2. Enter the new Web client ID and secret directly in [Supabase Google settings](https://supabase.com/dashboard/project/iyipvwlhiwfaeyfoyakr/auth/providers?provider=Google), then enable Google. Keep nonce checks and email requirements enabled. No secret belongs in Expo/EAS public variables, repository files or chat messages.
3. For native Apple, enable **Sign in with Apple** for the existing Apple Developer App ID `com.feridun.syncapp`. In [Supabase Apple settings](https://supabase.com/dashboard/project/iyipvwlhiwfaeyfoyakr/auth/providers?provider=Apple), allow that bundle ID and enable Apple. Native token verification does not require an Apple web OAuth signing secret. The source now adds `usesAppleSignIn`, the official plugin and the `com.apple.developer.applesignin` entitlement. Distribution profiles must be regenerated/checked against that capability. This is separate from MusicKit's runtime app service.
4. If Android/web Apple login is included, configure an Apple Services ID and web OAuth secret as well; those secrets require periodic rotation. That web setup has not been completed here. An old binary without the new native module is not native Apple sign-in validation.
5. Confirm Supabase's redirect allowlist includes `syncapp://auth/callback` and the existing recovery URI. Build/install the new native client. Test successful Google and Apple login with the owner, cancellation, email/recovery fallback, guest access, cold restart, sign-out, existing-account identity behavior and account isolation. Enabled providers and visible buttons alone do not establish live-account success.

Creating a new OAuth client and enabling new production authentication methods changes persistent security configuration. These activation steps require the user's action-time approval in the browser workflow before creating/saving credentials or provider access. All local implementation and regression work can be reviewed before that step.
